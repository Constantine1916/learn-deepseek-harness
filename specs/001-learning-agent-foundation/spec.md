# 001 — Learning Agent Foundation

状态：Draft

目标版本：0.1.0

DSH 设计基线：0.1.0-rc.5

## 1. 问题

DSH 的插件树、事件、capability seam、session log 和运行时组合机制具有较高学习门槛。仅阅读架构文档很难证明学习者能够把概念应用到真实插件开发中；普通聊天 Agent 又容易给出泛化解释、跳过诊断、直接生成答案，或者在没有证据的情况下宣布学习者已经掌握。

本规格定义一个构建在 DSH 公开扩展点上的教学 Agent。它必须把讲解、真实源码、练习、机器证据、反馈和持久学习状态连成一个可验证闭环。

## 2. 产品目标

- 帮助初学者建立 DSH 的正确整体模型。
- 帮助开发者完成第一个真实 DSH Tool、Provider 和 Bundle。
- 根据学习目标和掌握证据选择不同路径。
- 使用真实运行结果验证能力，而不是只评价语言表达。
- 在中断后恢复课程、尝试记录和掌握证据。
- 以外部 bundle 运行，不要求维护 DSH 核心分叉。

## 3. 目标用户

### 主要用户

- 熟悉 TypeScript，但第一次接触 DSH 或 Cordis 的开发者。
- 熟悉其他 Agent 框架，希望理解 DSH 插件架构的开发者。
- 准备为 DSH 开发 Tool、Provider、Skill、MCP 集成或 Bundle 的贡献者。

### 次要用户

- 使用该项目进行新成员 onboarding 的团队。
- 维护课程、练习和 DSH 开发者体验的贡献者。

## 4. 预期学习成果

完成 MVP 后，学习者必须能够：

1. 解释 Plugin、Context、Service、Effect 和 typed event 的关系。
2. 区分 Profile、Bundle、Preset 和普通 Plugin。
3. 解释 Service Definition、Provider 和 Consumer。
4. 说明 System Prompt、Tool Schema、Agent Loop 和 Session Log 如何协作。
5. 创建并卸载一个最小插件。
6. 创建一个模型可调用 Tool，并用测试验证行为。
7. 实现或替换一个最小 Provider。
8. 将插件组合进 Bundle/Profile 并成功运行。

## 5. 产品原则

- 先诊断，再教学。
- 教学结论必须引用观察到的证据。
- 真实任务优先于记忆题。
- 提示逐级展开，默认不直接泄露完整答案。
- 确定性代码检查判断可以机械验证的事实，模型负责解释与追问。
- 课程绑定明确的 DSH 版本范围。
- 模型看到的学习状态必须能够从持久记录重建。
- 教学流程使用 DSH 扩展点，不修改默认 Agent Loop。
- 课程定义目标和 rubric，不硬编码一组固定问题来模拟自适应教学。

## 6. 核心用户旅程

### 6.1 首次进入

1. Agent 说明教学方式、权限范围和课程能力。
2. 收集学习目标、已有经验和预期学习深度。
3. 执行概念诊断和一个小型真实任务。
4. 生成带证据的初始能力画像。
5. 给出可查看、可调整的学习计划。

### 6.2 单节课程

1. 展示本节目标、先修知识和完成证据。
2. 结合真实 DSH 文档、源码或配置讲解概念。
3. 通过预测、解释或局部修改检查概念模型。
4. 在隔离工作区创建练习。
5. 运行确定性检查并解释失败类别。
6. 根据需要提供分层提示。
7. 记录掌握证据、误区和下一步。

### 6.3 恢复学习

1. 从持久记录恢复目标、计划、当前单元和尝试。
2. 简短确认恢复点和仍未解决的问题。
3. 从未完成任务或下一单元继续，不重新执行完整 onboarding。

### 6.4 课程完成

1. 完成综合插件或 capability seam 任务。
2. 运行自动化验收。
3. 输出学习报告，区分课程浏览、练习完成和能力验证。

## 7. 功能需求

### F-001 标准 DSH 组合

Must：项目必须以外部插件和 bundle 安装到受支持的 DSH Runtime，不要求修改 DSH 核心文件。

Must：卸载 bundle 后，DSH 的其他 profile 必须保持可用。

### F-002 教师 Persona

Must：Agent 必须说明自己的教学角色、学习闭环和权限限制。

Must：Persona 必须支持解释、追问、分层提示、反馈和复习。

Should：语气和例子可以适配学习者背景，但不能改变完成标准。

### F-003 版本化课程

Must：每个课程单元必须定义唯一 ID、标题、目标、前置单元、DSH 版本范围、内容入口、练习、提示层级、rubric 和完成条件。

Must：课程加载时必须拒绝重复 ID、缺失前置、循环依赖和不受支持的版本表达式。

Must：首版课程必须覆盖第 4 节中的八项学习成果。

### F-004 初始诊断

Must：诊断必须收集目标和背景。

Must：诊断必须同时包含概念证据和至少一个真实源码、配置或代码证据。

Must：诊断结果必须列出证据、不确定项和推荐起点。

Must：问题应由课程目标和学习上下文生成，不得只播放固定题单。

### F-005 学习计划

Must：计划必须遵守课程前置关系。

Must：只有存在足够掌握证据时才能跳过 Must 级课程单元。

Must：学习者必须能够查看并请求调整计划。

Must：每次跳课、补课或难度变化都必须记录原因。

### F-006 课程执行

Must：每节课开始时展示学习目标和完成证据。

Must：讲解必须使用与当前支持版本匹配的 DSH 来源。

Must：课程必须至少包含一次要求学习者产生输出的检查点。

### F-007 实践环境

Must：练习必须运行在明确、可重置的工作区。

Must：DSH 源码默认只读；学生改动发生在练习副本或专用 fixture。

Must：所有写入、命令和进程能力必须受 DSH sandbox、FS policy 和 approval 控制。

Must：重置只能影响当前练习的已解析目录。

### F-008 自动评测

Must：可以机械判断的结果必须来自测试、类型检查、构建、配置树、导出接口或运行事件。

Must：评测必须区分实现失败、配置失败、环境失败和概念误解。

Must：实践能力不能只凭一次自然语言回答判定掌握。

Should：解释类回答使用显式 rubric，并允许标记为需要复核。

### F-009 分层提示

Must：每个实践练习至少提供三级提示。

Must：前两级提示不得包含完整参考实现。

Must：系统必须记录使用过的提示层级，作为掌握证据的一部分。

### F-010 学习状态

Must：状态至少包含学习目标、计划、当前单元、尝试、检查结果、掌握证据、误区、提示使用和下一步。

Must：状态必须通过追加事件投影得到，不能把一份可任意覆盖的总结作为唯一真源。

Must：重复重放同一事件不能重复授予完成状态。

### F-011 Session 恢复与隔离

Must：恢复 Session 后，计划、当前单元、尝试和掌握证据必须一致。

Must：不同 Session 的学习状态必须隔离。

Must：任何进入模型请求的学习状态都能从 Session Log 和版本化课程输入重建。

### F-012 DSH 来源探索

Must：Agent 必须能定位当前课程对应的 DSH 文档和源码入口。

Must：来源引用必须包含版本和稳定标识；当标识失效时必须明确报告兼容性问题。

Should：Agent 可以解释当前 profile 的插件树和关键配置行。

### F-013 学习报告

Must：报告必须列出已验证能力、对应证据、未解决误区和推荐后续任务。

Must：报告必须区分“已阅读”“已完成练习”和“已通过综合验证”。

## 8. 质量属性

### Q-001 可替换性

教学插件依赖 DSH 公开 Service Definition 和事件，不依赖默认 Provider 的内部实现。

### Q-002 可重放性

同一课程版本和同一学习事件前缀必须投影出相同结构化学习状态。

### Q-003 安全性

默认配置不能写入真实 DSH checkout、读取未授权秘密或执行绕过 sandbox 的进程。

### Q-004 可解释性

所有计划变化、掌握变化和课程完成都必须有可展示的原因和证据引用。

### Q-005 兼容性

每个发布版本必须声明支持的 DSH 版本范围，并在 CI 中至少验证最低和最高支持版本。

### Q-006 教学质量

关键用户旅程必须通过真实组装的 keyless snapshot；发布候选还必须通过人工教学 rubric 和可选真实模型评估。

### Q-007 性能与成本

课程只注入当前单元需要的来源；结构化学习状态替代整段历史复读。单次普通课程 step 的固定教学上下文目标上限在实现阶段通过 token snapshot 固化。

## 9. MVP 范围

MVP 包含：

- 一个可安装的 headless/CLI 教学 bundle。
- 教师 Persona。
- 版本化基础课程图。
- 初始诊断和计划。
- 至少三个连续课程单元。
- 至少两个代码练习和一个综合练习。
- 分层提示。
- 确定性评测。
- 学习事件、投影和 Session 恢复。
- keyless snapshots、集成测试和安装文档。

## 10. 非目标

- 维护修改过的 DSH Runtime。
- 替换默认 Agent Loop。
- 通用 LMS、账户、付费、班级或企业后台。
- 完整浏览器 IDE。
- 任意技术主题的通用课程平台。
- 自动兼容所有未来 DSH 版本。
- 只靠固定题库、关键词匹配或 LLM 主观评分完成诊断。
- MVP 阶段的多 Agent 教师团队和复杂 Web 学习面板。

## 11. 主要风险

| 风险 | 缓解措施 |
|---|---|
| DSH 预发布接口和源码锚点变化 | 严格版本范围、兼容矩阵、来源检查和升级规格 |
| 模型跳过流程或直接给答案 | 结构化教学状态、工具门禁、快照和提示策略测试 |
| 评测误判 | 机器证据优先、显式 rubric、不确定结果进入复核 |
| 练习破坏真实仓库 | 独立工作区、只读来源、sandbox、明确重置目标 |
| 过早平台化 | 先完成一个真实教学闭环，再扩展课程和 UI |
| Token 与模型成本失控 | 按单元注入、结构化投影、来源精确定位和 token 预算测试 |

## 12. 成功指标

MVP 验收以 [acceptance.md](acceptance.md) 为准。产品验证阶段另外观察：

- 新用户完成首个真实插件练习的成功率。
- 需要完整答案才能完成练习的比例。
- Session 恢复后无需重新解释上下文即可继续的比例。
- 诊断起点与后续实践表现的一致程度。
- DSH 版本升级导致课程来源或练习失效的数量。
